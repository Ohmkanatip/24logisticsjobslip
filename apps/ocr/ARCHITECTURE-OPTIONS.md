# ทางเลือกสถาปัตยกรรม "เขียนเบอร์ตู้กลับเข้าใบงาน"

> ## ✅ เจ้าของเคาะแล้ว (28 ส.ค. 2569): ทาง ③ d1 staging
> คำพูดเจ้าของ: *"ถ้าเข้า Apps Script จะช้ามาก และไม่อยากให้ base มันมาเกี่ยว — แค่เชื่อมเอาข้อมูลมาต่อเฉยๆ"*
> **implement แล้ว + เทสครอบวงจรเต็ม:** คนขับยืนยันใน LINE → Worker เขียนตาราง `ocr_results` (D1) →
> เว็บ jobslip ดึงผ่าน `GET /api/ocr/results` (มีด่าน `PULL_TOKEN`) → เติมช่องเบอร์ตู้ → บันทึกเข้าชีทตามเส้นทางเดิมของเว็บ →
> ติดธง `pulled` ผ่าน `POST /api/ocr/pulled` (แถวไม่ลบ ไว้สาวย้อน · ดึงซ้ำถูกปฏิเสธ กันเบอร์เดียวไป 2 ใบ)
> **ผล: บอทแตะชีทเป็นศูนย์ · ชีทยังเป็นเจ้าของข้อมูล 100% · Apps Script ไม่อยู่ในเส้นทาง OCR เลย**
> เนื้อหาด้านล่างเก็บไว้เป็นบันทึกการเปรียบเทียบตอนตัดสินใจ

> ทั้ง 3 ทางใช้ interface เดียวกัน: `fillContainer({ jobUid, containerNo, confirmedBy })` (ดู `src/writeback/index.js`)
> ตอนนี้ทุก adapter เป็น stub ซื่อสัตย์ (`not-implemented`) — โค้ดที่รันจริงมีแค่ mock
> **เคาะแล้วเปลี่ยนใจทีหลังได้** — โค้ดส่วนอื่น (webhook/OCR/เช็คดิจิต) ไม่ต้องแก้เลย แค่สลับ adapter

## จุดเสียบในระบบจริง (สำรวจแล้ว 28 ส.ค. 2569)

- งานที่จ่ายผ่านหน้า "จ่ายงานคนขับ" (V65) สร้าง**ร่างบิล**ในแท็บ `บิล` โดย**เว้นช่องเบอร์ตู้ว่างไว้** — นี่คือช่องที่ OCR ต้องเติม
- ร่างมี `uid` ของตัวเอง · ยืนยันร่างผ่าน act `drconfirm` (มีอยู่แล้ว) · แท็บคนขับมี `driverId` แล้ว (act `drdriverlist`) → เฟส LIFF ใช้ผูก LINE user ↔ คนขับ ↔ งานของวันนั้นได้เลย
- หลังบ้านเดิมมีด่านครบ: สิทธิ์ (`authAny_`) · rate limit ต่อคน · `safeText_` กัน formula injection · ประวัติแก้ไข (`logMoney_`/คอลัมน์เหตุการณ์) · กติกา A0 (ห้ามงานช้าใน LockService)

## ความเห็นเบื้องต้น (ยังไม่ใช่การตัดสินใจ)

**เสนอทาง ①** — เหตุผลเฉพาะของระบบนี้:
1. บทเรียน V63.6/A2 ของโปรเจกต์แม่ชัดว่า "เหตุการณ์เรื่องเงิน/ข้อมูลต้องผ่านด่านเดิมให้ประวัติสาวย้อนได้" — ทาง ② ข้ามด่านพวกนี้หมด
2. act ใหม่เดินตามแพทเทิร์นเดิมได้เลย (rate limit + safeText_ + ลงประวัติ) — แรงเขียนน้อยสุด ตรวจง่ายสุด
3. ความช้า 1–3 วิ เกิด**หลัง**คนขับกดยืนยัน — คนขับเห็น "✓ รับแล้ว" ทันทีจาก LINE ไม่ต้องรอชีท
4. ทาง ③ เก็บไว้เป็นเส้นทางอนาคต — interface เดียวกัน สลับได้วันที่ย้ายฐานข้อมูล

**ข้อควรระวังถ้าเคาะทาง ①:** act ใหม่ต้องกันเคส "ใบงานถูกยืนยัน/แก้ไปแล้วระหว่างรอ OCR" (ตอบ conflict ให้บอทแจ้งคนขับ ไม่เขียนทับเงียบๆ) และต้องเช็คเช็คดิจิตซ้ำฝั่ง .gs อีกชั้น (อย่าเชื่อ payload จาก Worker)
