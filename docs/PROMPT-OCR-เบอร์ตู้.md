## เป้าหมาย

คนขับถ่ายรูปตู้คอนเทนเนอร์ → ระบบอ่าน **เบอร์ตู้** อัตโนมัติ → เติมเข้าช่อง "เบอร์ตู้" ที่ตอนนี้เว้นว่างไว้ในใบงานร่าง โดยคนขับไม่ต้องพิมพ์เอง ลดพิมพ์ผิด ลดงานแอดมิน

นี่คือ **งาน ③** ในแผนแม่บท (ไฟล์ `24LOGISTICS-MASTER-SPEC.md`) — พิสูจน์ความแม่นแล้ว 9/9 ในการทดสอบมือ ตอนนี้จะทำเป็นระบบจริง

## สิ่งที่ต้องทำ (ลำดับสำคัญ — อย่าข้ามข้อ 1–2)

1. **อ่านก่อนเขียนโค้ด:** อ่าน `CLAUDE.md`, โค้ดระบบใบงาน (`index.html` + Apps Script), และ `24LOGISTICS-MASTER-SPEC.md` — โดยเฉพาะบรรทัดที่พูดถึง "ช่องเบอร์ตู้ที่ว่าง = จุดเสียบ OCR" เพื่อเข้าใจว่าใบงานร่างถูกสร้างที่ไหน เก็บที่ไหน และช่องเบอร์ตู้ผูกกับ record ไหน
2. **เสนอสถาปัตยกรรมก่อนลงมือ:** เสนอ **2–3 ทางเลือก** ว่าจะเชื่อม OCR เข้าระบบตรงไหน/อย่างไร พร้อม **ข้อดี-ข้อเสียของแต่ละแบบ** (เช่น รับรูปทางไหน, เรียก OCR ที่ layer ไหน, เขียนกลับเข้าใบงานร่างยังไง, จับคู่รูปกับใบงานที่ถูกต้องได้ยังไง) — **รอเจ้าของเคาะก่อน** แล้วค่อยเขียนโค้ด
3. หลังเคาะ: implement + เขียนเทสต์ (ระบบนี้มีวัฒนธรรมเทสต์อยู่แล้ว 654 เคส — ของใหม่ต้องมีเทสต์ด้วย)

> ผมตั้งใจ **ไม่ล็อกว่าให้เชื่อมกับอะไร** — ให้คุณสำรวจ repo จริงแล้วคิดสถาปัตยกรรมที่เข้ากับของเดิมที่สุด

## บริบทระบบที่มีอยู่ (สิ่งที่ OCR อาจต้องเชื่อม)

- **ระบบใบงาน/วางบิล V63.7** — `index.html` + Google Apps Script + Google Sheets ชีต "Jobslip" · repo `Ohmkanatip/24logisticsjobslip` · ใบงานร่างถูกสร้างจากงาน ① (แอปจ่ายงาน) โดย **เว้นช่องเบอร์ตู้ว่างไว้**
- **LINE OA** (งาน ③ เดียวกัน) — ช่องทางที่คนขับน่าจะส่งรูปตู้เข้ามา (แชท 1:1) — พิจารณาว่าจะใช้ LINE webhook เป็นตัวรับรูปไหม
- **แผนอนาคต:** GPS Cartrack → Cloudflare D1, ย้าย auth ไป Cloudflare Zero Trust, อาจย้าย Supabase — ออกแบบให้ไม่ผูกตายกับ Google Sheets จนย้ายยาก
- ปัจจุบัน host บน GitHub Pages + Apps Script

## โดเมนเบอร์ตู้ (ใช้ตรวจความถูกต้อง — สำคัญมาก)

เบอร์ตู้เป็นมาตรฐาน **ISO 6346**: ตัวอักษร 4 ตัว (owner code 3 + category 1 มักเป็น U) + ตัวเลข 6 หลัก + **เช็คดิจิต 1 หลัก** เช่น `MSKU 123456 7`

- **บังคับใช้อัลกอริทึมเช็คดิจิต ISO 6346 ตรวจผลลัพธ์ OCR ทุกครั้ง** — ถ้าเช็คดิจิตไม่ผ่าน แปลว่าอ่านผิด ให้ flag ไม่ใช่เติมเข้าใบงานมั่ว วิธีนี้ทำให้ความแม่นสูงขึ้นมากโดยไม่ต้องพึ่ง OCR อย่างเดียว
- อาจมี **ISO size-type code** (เช่น `45G1` = 40' HC) และ **seal number** ในรูปด้วย — เสนอได้ว่าจะอ่านเพิ่มไหม แต่ **scope ที่ commit ไว้คือเบอร์ตู้** อย่าเพิ่มงานเกินโดยไม่ถาม
- เบอร์ตู้เป็น A–Z/0–9 ไม่ใช่ภาษาไทย → ปัญหาความแม่นภาษาไทยไม่กระทบฟิลด์นี้โดยตรง

## ช่องทางให้คนขับใช้ (เคาะแล้ว: LINE เป็นฐาน — เริ่ม chat แล้วยกไป LIFF)

บริบทคนขับ: ~46 คน ใช้มือถือ ความคุ้นเทคต่างกัน อยู่หน้างานท่า/ลาน (สัญญาณอาจอ่อน) → หลักคือ **ไม่ต้องลงแอปใหม่ ไม่ต้องสมัคร/จำรหัส** ทำ 2 ระดับ:

**① LINE OA chat bot — MVP (ทำก่อน พิสูจน์ลูป)**
- คนขับถ่ายรูปตู้ส่งแชท 1:1 → บอท OCR ตอบเลข + ผลเช็คดิจิต + ปุ่ม ✓ยืนยัน / ↻ถ่ายใหม่
- ข้อดี: ทำเร็ว, คนขับคุ้นไลน์อยู่แล้ว, ต่อยอดจากที่เทสต์มือ 9/9 ได้ทันที
- ข้อเสีย: จับคู่ "รูปนี้ของงานไหน" ในแชทงก (บอทต้องถามให้เลือกงาน), แก้เลขผิดในแชทลำบาก, หลายตู้ต่อกะสับสน

**② LINE LIFF (เว็บแอปในไลน์) — เป้าหมายจริง (ยกขึ้นหลัง ① เวิร์ก)**
- เปิดจาก rich menu ไลน์ → เห็นงานที่ได้รับวันนี้ → แตะงาน → เปิดกล้อง → เห็นเลขที่อ่านได้ (ช่องแก้ได้) → ยืนยัน
- ข้อดี: อยู่ในไลน์ (ดึง LINE user id มาเลย ไม่ต้องล็อกอิน), **รูปผูกกับใบงานถูกใบอัตโนมัติ**เพราะเลือกงานก่อนถ่าย, มีไกด์กรอบถ่าย, รองรับถ่ายก่อน-อัปทีหลังตอนสัญญาณอ่อน
- ข้อเสีย: dev มากกว่าแชท ต้องตั้ง LIFF + host HTTPS (ใช้ Worker/Pages ที่มีอยู่)

**ไม่เอา:** standalone PWA/แอป native (คนขับต้องล็อกอิน/ลงแอปใหม่ = แรงต้าน ไม่คุ้มสำหรับ 46 คน)

> ทั้ง ① และ ② ให้ OCR รันฝั่ง **Worker** (มือถือแค่ถ่าย+อัป คีย์ไม่หลุด) และลดการพิมพ์ของคนขับให้เป็นศูนย์ — OCR เสนอ คนแตะยืนยันหรือแก้ทีละหลัก

## กติกา/ข้อจำกัด (ห้ามฝ่าฝืน)

- **อย่าแตะ flow production เดิมจนพัง** — ต่อยอดจากช่องเบอร์ตู้ที่เว้นไว้ ห้ามรื้อการสร้างใบงานร่าง มี rollback plan
- **คนขับต้องยืนยันก่อนบันทึก** — OCR เสนอเลข คนกดยืนยัน (โดยเฉพาะถ้าเช็คดิจิตไม่ผ่าน) ไม่เขียนทับเงียบๆ
- อย่าเก็บ API key / ความลับใน client — เรียก OCR ฝั่งเซิร์ฟเวอร์ (Apps Script / Worker) เท่านั้น
- ทุกฟีเจอร์ต้องผ่านกติกากรอง 2 ข้อ: (1) ใครกรอก/ส่งข้อมูล? (2) ใครใช้ผลตัดสินใจ? — ตอบไม่ได้ = ตัด

## สิ่งที่ต้องให้เจ้าของเคาะ (ยกมาเป็นคำถาม อย่าเดา)

- **เลือก OCR engine:** กำลังพิจารณา Qwen-VL — เทียบทางเลือก (Google Cloud Vision, Typhoon/OpenTyphoon OCR ไทย, self-host) พร้อม **ต้นทุนต่อ 1,000 รูป** และความแม่นกับรูปตู้จริง (มุมเอียง แสงจ้า ตู้สกปรก) แล้วให้เจ้าของเลือก
- ปริมาณจริง ~60–100 ตู้/วัน → ประเมินต้นทุน/เดือน
- (ช่องทางคนขับเคาะแล้ว: LINE chat → LIFF ดูหัวข้อด้านบน)

## เสร็จเมื่อ (Definition of Done)

- คนขับส่งรูปตู้ → เห็นเลขที่อ่านได้ + ผลเช็คดิจิต → ยืนยัน → เลขเข้าช่องเบอร์ตู้ของใบงานที่ถูกต้อง
- มีเทสต์ครอบเคสเช็คดิจิตผ่าน/ไม่ผ่าน และเคสอ่านไม่ออก
- ไม่กระทบเทสต์เดิม 654 เคส
- อัปเดต `CLAUDE.md`: สถาปัตยกรรม OCR ที่เลือก + เหตุผล + บทเรียน
